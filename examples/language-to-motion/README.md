## Why there is no annotation step

Every line of Demo A's `frames.jsonl` already contains both halves of a
supervised example, because they were written onto the same timeline:

| Role | Field |
|---|---|
| Vision (V) | `frame_image` — the source frame |
| Language (L) | `caption` — temporal caption |
| Action (A) | `bone_rotations_xyzw` / `hips_position` / `finger_curls_rad` |
| State | `phase` — Idle / Reach / Grasp / Carry / Release |

Prompt and answer are already paired. That is the payoff of having a behavior
representation in the first place: the observation record *is* the training set.

## Architecture

```text
frame image (timeline/frames/*.jpg)     "The person picks up..."  (instruction)
        │ frozen ResNet18                        │ char-level CNN encoder
        ▼                                        ▼
  [vision prefix]                          [text prefix]
        └──────────────────┬──────────────────────┘
                           ▼   modality dropout during training
                               → text-only / image-only / both, one model
              causal Transformer (4 layers, d=256)
              ┌────────────┴────────────┐
              ▼                         ▼
        motion head              phase head  ← the state machine
    quat×19 + hips + curls    Idle/Reach/Grasp/Carry/Release/<end>
              │                         │ predicted phase feeds the next step
              ▼                         ▼
        CBD-compatible generated behavior
              │
   ┌──────────┼──────────────┐
   ▼          ▼              ▼
frames.jsonl  motion.vrma    humanoid.xml + motion.npz
 (data)       (Unity)        (MuJoCo)
```

Three design points:

- **Three layers of state machine.** (1) Demo A's rule-based phase detection
  produces the supervision, (2) the phase head learns probabilistic transitions,
  (3) generation applies a hard grammar allowing only transitions observed in
  the data. The last cell prints both transition matrices side by side, so you
  can see how much of the state machine was actually learned.
- **Differentiable throughout.** Quaternions use a normalisation layer and a
  geodesic loss (`1 − |⟨q, q̂⟩|`); positions and curls use MSE; phase uses
  cross-entropy; velocity and acceleration losses buy temporal smoothness.
- **One schema, one set of adapters.** Replaying observed motion and replaying
  generated motion go through the exact same `motion.vrma` and
  `humanoid.xml` + `motion.npz` path.

### Preparing the corpus

```text
behavior_corpus/
├── Episode1/    ← one Demo A output bundle, unzipped
│   └── ... 04_behavior_dataset/timeline/frames.jsonl
├── Episode2/
└── EpisodeN/    ← add more, re-run [2]–[4]
```

`timeline/frames.jsonl` is found recursively, so exact nesting does not matter.
Episodes with captions (Demo A `[5.5]`) **and** frame images
(`video.export_frame_images = True`, on by default) are recommended. Episodes
missing one of them still train — the missing modality becomes a learned null
embedding.

### Runtime

T4 / L4 / A100 all work, and so does CPU (just slower). The model is a few
million parameters and uses AMP automatically. At the current corpus size the
CPU-side work dominates, so GPUs differ little; lowering `EPOCHS` is the
effective way to shorten a run.

## What this actually does

Training on a few episodes demonstrates **that the mechanism runs end to end**.
In substance it is memorisation and interpolation of the training data; the
closer a prompt is to a learned caption, the better the output.

| Works today | Does not work |
|---|---|
| Regenerating a learned behavior from a prompt close to its caption | Unseen instructions ("with your left hand", "wave both arms") |
| Selecting between 2–3 learned behaviors by instruction | Non-English prompts |
| Grammatically valid phase sequences | Object trajectory generation — output is the human body only |
| Conditioning on a frame image from the training episodes | Physically consistent contact or grasping |

Realistic scale estimate: early interpolation around **10 episodes**; something
resembling generalisation around **100 episodes** of the same task family. Real
generalisation needs orders of magnitude more, plus a proper video encoder.

The schema, state machine and loss design are the same shape as a real VLA, so
the structure is built to keep improving as episodes accumulate. That is the
claim — not that it works today at scale.

### Lower body is frozen by default

`FREEZE_LOWER_BODY = True` pins the six leg bones to a fixed pose.

The current corpus is seated video: the legs are occluded by a table, MediaPipe's
estimate there is low confidence, and with few episodes there is no averaging to
cancel that noise. The model would faithfully learn the noise — which is exactly
why generated legs jitter.

**This is a training-data problem, not an accuracy problem.** Freezing frees
model capacity for the upper body that *is* observed. Turn it off (`False`) as
soon as you include standing or walking episodes, or once a seated corpus is
large enough to average the leg estimates. The setting is recorded in the
generated `manifest.json` as `lower_body_frozen` / `lower_body_pose`.

## Tuning generation

| Symptom | Fix |
|---|---|
| Motion jittery | Lower `GEN_SMOOTHING_ALPHA` (default 0.2). Training already uses velocity/acceleration losses and scheduled sampling. |
| Different result each run | Set `GENERATION_SEED` to a fixed value (default 0); `None` randomises. |
| Output too short / too long | Lower `PHASE_TEMPERATURE` (0.7 → 0.3) to be more decisive; `MAX_GENERATION_FRAMES` caps length. |
| Impossible phase transitions | Keep `ENFORCE_TRANSITION_GRAMMAR = True` (default). |
| Every instruction gives the same motion | Not enough episodes — add episodes of *different* behaviors. |
| Loss does not converge | Increase `EPOCHS`. Quaternion loss under 0.01 is well converged (0.0036 ≈ 5°). |

### Checkpoints (`[4.5]`)

| MODE | Use |
|---|---|
| `"save"` | Save the current model; set `DRIVE_BACKUP_DIR` for a timestamped Drive copy |
| `"load"` | Load a saved model and skip `[4]` entirely |
| `"finetune"` | Continue training at a low learning rate |

The checkpoint stores normalisation stats, phase vocabulary, bone order and the
freeze settings, and refuses to load into an incompatible configuration rather
than producing quietly broken output.

Two things to know about fine-tuning:

- **Adding a new behavior changes `PHASE_VOCAB`**, which changes the phase head's
  output dimension. That checkpoint cannot be reused — retrain from `[4]`.
- **Fine-tuning on new data alone causes catastrophic forgetting.** `"finetune"`
  therefore re-trains on the whole current corpus at a low learning rate. Add
  ZIPs in `[1.6]` and re-run `[2]` first.

At the current scale, retraining from scratch is usually faster and more reliable
than fine-tuning. Fine-tuning starts to pay off around a few dozen episodes.

## Where this goes next

| Step | What it means |
|---|---|
| More data | Add episode folders, re-run `[1.6]` → `[4]`. Nothing else changes. |
| Unfreeze the lower body | Add standing / walking episodes, set `FREEZE_LOWER_BODY = False` |
| Include objects | Generate the `objects` proxy positions too, for behavior with objects |
| Tokenise motion | Discretise with a VQ-VAE and treat it as next-token prediction |
| Diffusion | Replace the motion head with denoising diffusion |
| Real vision | Fine-tune the frozen ResNet instead of freezing it |

**Observed behavior and generated behavior replay through the same adapters, in
the same schema.** That property — not the size of this model — is what the demo
is meant to show.
